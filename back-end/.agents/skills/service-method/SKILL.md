# 서비스 메소드 생성

## 참고 코드와 적용 범위

- 대상 도메인의 entity, DAO, MyBatis Mapper XML, 서비스와 호출부를 먼저 읽고 필드 타입, SQL 반환값, 기존 메소드명과 예외 처리 방식을 확인한다.
- 기본 위치는 `src/main/java/com/mycompany/demo/database/` 아래의 `service`, `entity`, `dao`다. 실제 대상 패키지 구조를 우선한다.
- `MemberService`의 엔티티 조회·수정·저장 후 재조회, 삭제 건수 반환, DAO 생성자 주입 방식을 일반화한다. 기존 코드의 웹 요청 DTO 및 `ResponseStatusException` 의존은 그대로 복제하지 않는다.
- 요청받은 기능과 필요한 호출부만 수정한다. 스킬 적용을 이유로 무관한 도메인까지 일괄 변경하지 않는다.

## 엔티티 객체로 DB 데이터 처리

- DB 행은 해당 엔티티 객체로 매핑해 사용한다. 단건 데이터는 엔티티, 여러 행은 `List<Entity>`로 받거나 반환한다. DB 행을 임의의 Map이나 웹 응답 DTO로 표현하지 않는다.
- 가입·생성·수정 입력은 해당 엔티티 객체로 받는다. 단일 ID는 `String`, `int` 등 실제 타입으로 직접 받으며 ID 하나를 감싸는 DTO는 만들지 않는다.
- 검색·페이징은 엔티티에 없는 조건을 억지로 엔티티 필드로 추가하지 않는다. 기존의 웹 독립적인 검색 조건 객체나 `Pager`를 재사용하고, 필요한 경우 서비스용 조건 객체를 정의한다. 기존 DAO가 요구하는 조건 Map은 내부에서 사용할 수 있다.
- 행 개수, 삭제 건수 등 집계·처리 결과는 `int` 등 의미에 맞는 타입으로 반환한다. 이를 반환하려고 가짜 엔티티를 만들지 않는다.

## 컨트롤러와 결합도 낮추기

- 검색 조건을 포함한 DTO와 조건 객체는 `database/dto/<도메인>`에 배치한다. 예: `dto/member`, `dto/product`, `dto/seller`. 여러 도메인이 공유하는 `Pager` 등은 `dto/common`에 둔다. 서비스에서 쓰더라도 `service` 패키지에 두지 않는다. 웹 전용 Request/Response DTO와 웹에 독립적인 서비스용 조건 DTO는 역할로 구분한다.

- 서비스는 Controller, 웹 Request/Response DTO, `ResponseEntity`, `HttpStatus`, `ResponseStatusException`, Servlet 요청·응답 객체를 참조하지 않는다.
- 컨트롤러는 요청 DTO를 엔티티 또는 서비스용 조건 객체로 바꿔 전달한다. 서비스가 반환한 엔티티와 처리 건수를 응답 DTO로 정제하는 책임도 컨트롤러에 둔다.
- 서비스는 응답 DTO를 생성하거나 성공 메시지, HTTP 상태 코드, JSON 필드 구성을 결정하지 않는다. DTO에 변환 메소드를 추가하지 않는다.
- 단건 조회는 엔티티 또는 null, 수정·삭제는 실제 처리 건수를 반환하고 컨트롤러에서 HTTP 오류를 판단한다. 페이지 번호 등 HTTP 입력 검증도 컨트롤러에서 처리한다. 단순 CRUD 결과를 HTTP 오류로 변환하기 위한 서비스 예외나 별도 핸들러는 만들지 않는다. 실제 업무 규칙 검증은 서비스에 두고 DB 예외는 그대로 전파한다.
- DAO는 `private final` 필드와 생성자로 주입한다. 프로젝트의 Lombok 방식에 맞춰 `@Service`, `@RequiredArgsConstructor`를 사용하고 서비스 자신이나 컨트롤러를 주입하지 않는다.

## 메소드 구현 방식

- 메소드명은 기존 도메인과 업무 동사를 따른다. 예: `getMember`, `joinMember`, `updateMember`, `deleteMember`, `listMember`. DAO의 `select`, `insert` 등 영속성 이름은 DAO에 둔다.
- 단건 조회는 DAO에서 엔티티를 얻고, 조회 실패 계약에 맞춰 존재하지 않는 경우를 명시적으로 처리한다. null을 바로 역참조하지 않는다.
- 생성은 엔티티를 DAO에 전달하고, 저장 결과가 필요한 경우 키를 이용해 재조회한 엔티티를 반환한다. DB 기본값이나 생성 키를 요청값으로 대신하지 않는다.
- 수정은 기존 엔티티를 조회해 수정 가능한 필드만 변경한다. 요청에 포함되지 않은 이름·가입일 등 기존 필드를 의도치 않게 덮어쓰지 않는다. 대상이 없으면 0, 수정 시 DAO 처리 건수를 반환한다. 응답에 엔티티가 필요하면 컨트롤러가 성공 여부를 확인한 뒤 조회한다.
- 삭제는 DAO의 실제 처리 건수를 반환한다. 조회·목록은 엔티티와 엔티티 목록을 반환하고, 페이징 계산은 별도 메소드로 제공할 수 있다.
- 여러 DB 작업이 하나의 원자적 업무를 이루는 경우 프로젝트의 트랜잭션 방식을 확인하고 서비스에 적절한 `@Transactional` 경계를 둔다.

## try-catch 지양

- 단순 DAO 호출을 try-catch로 감싸지 않는다. 처리할 수 없는 예외는 전파하고 공통 예외 처리 계층에 맡긴다.
- 예외를 삼킨 뒤 null, 빈 목록, 0 또는 성공 결과를 반환하지 않는다. 로그만 남기고 같은 예외를 다시 던지는 catch도 추가하지 않는다.
- 실제 복구, 필요한 자원 정리, 도메인 의미가 있는 예외 변환이 있을 때만 좁은 범위에서 구체적인 예외를 잡는다. 변환할 때 원인 예외를 보존한다. 단순 자원 해제에는 try-with-resources를 사용할 수 있다.

## 완료 확인

- 웹 DTO 및 HTTP 타입 의존이 새 서비스 코드에 없는지, DB 행이 엔티티 객체로 처리되는지, 불필요한 try-catch가 없는지 검토한다.
- 메소드 시그니처 변경 시 호출부도 수정하고, 웹 응답 필드와 오류 계약이 의도치 않게 바뀌지 않았는지 확인한다.
- 변경 범위에 맞는 컴파일과 관련 기존 테스트를 수행한다. DB 검증을 실행하지 않았다면 컴파일 결과와 구분해 알린다.
