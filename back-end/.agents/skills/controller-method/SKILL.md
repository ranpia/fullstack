# 컨트롤러 메소드 생성

## 기존 코드 확인

- 대상 기능의 controller, service, dto, entity를 먼저 읽고 패키지, 필드명, 타입, Lombok 사용 방식과 서비스 메소드명을 확인한다.
- 이 프로젝트의 기본 위치는 `src/main/java/com/mycompany/demo/<기능>/` 아래의 `controller`, `service`, `dto`, `entity` 패키지다. 실제 대상 코드의 구조를 우선한다.
- 기존 컨트롤러에 DAO 직접 호출, 엔티티 직접 반환, 임시 메소드명이 있어도 아래 규칙에 맞춰 요청받은 메소드 범위만 구현한다.

## 요청·응답 DTO

- DTO는 `database/dto/<도메인>`으로 묶는다. 회원은 `dto/member`, 상품은 `dto/product`, 판매자는 `dto/seller`에 두며, 공통 페이징 등 도메인에 독립적인 타입은 `dto/common`에 둔다. 검색 조건 객체도 같은 도메인 DTO 패키지에 둔다. 이동 시 Java import와 MyBatis 별칭 참조를 함께 확인한다.

1. 요청 값이 하나면 `String memberId`처럼 해당 타입으로 직접 받으며 별도 Request DTO를 만들지 않는다. 여러 요청 값은 해당 기능의 `Request` DTO로 묶는다. 입력 데이터가 없는 요청에는 빈 DTO를 만들지 않는다.
2. 반환 데이터는 해당 기능의 `Response` DTO로 만든다. 엔티티, 문자열, 숫자, boolean, `Map<String, Object>` 또는 목록 자체를 컨트롤러에서 직접 반환하지 않는다. `ResponseEntity<ResponseDTO>`는 사용할 수 있다.
3. 여러 값과 목록은 응답 DTO의 명시적인 필드로 담는다. 목록 항목도 필요한 필드만 가진 응답 DTO로 변환하고, 페이징 정보는 별도 필드로 포함한다.
4. DTO는 요청·응답에 필요한 필드만 선언한다. 비밀번호 등 민감 정보는 응답에 포함하지 않는다. 동일한 계약의 DTO가 있으면 재사용하고, 필드나 용도가 다르면 기능별로 분리한다.
5. 이름은 기존 DTO 규칙을 먼저 참고한다. 규칙이 없거나 기존 이름으로 기능 구분이 어려우면 `GetMemberRequest`, `GetMemberResponse`, `CreateBoardRequest`처럼 `<동작><대상>Request/Response`를 사용한다.
6. 여러 값의 JSON 본문은 `@RequestBody` DTO로, 검색·조회 쿼리는 `@ModelAttribute` DTO로 받는다. 단일 쿼리 값은 `@RequestParam`, 단일 경로 변수는 `@PathVariable`로 받는다. GET에 JSON 본문을 강제하지 않고 기존 경로 계약을 유지한다.
7. 입력 검증이 필요한 경우 프로젝트의 Bean Validation 방식을 따르고 `@Valid` 또는 기존 검증 방식을 적용한다. 요청하지 않은 검증 규칙은 임의로 추가하지 않는다.

## 서비스 참조와 이름

- 해당 도메인의 서비스를 생성자 주입한다. 예: `MemberService memberService`. 기존 Lombok 방식이 있으면 `@RequiredArgsConstructor`와 `private final` 필드를 따른다.
- 컨트롤러는 서비스에 업무 처리를 위임한다. DAO나 Repository를 직접 호출하거나 업무 로직을 구현하지 않는다.
- 메소드명은 기존 서비스의 기능명과 동사 규칙을 참고해 명확히 짓는다. 예를 들어 서비스가 `getMember`이면 컨트롤러도 `getMember`를 우선한다. `putMethodName` 같은 임시 이름은 사용하지 않는다.
- 해당 서비스 기능이 없으면 요청받은 기능에 필요한 서비스 메소드를 추가한다. 단순히 이름만 맞추려고 무관한 서비스를 호출하거나 빈 구현을 만들지 않는다.
- 컨트롤러·서비스 간에도 여러 개의 원시 값 대신 요청 DTO 또는 기존 서비스 입력 객체로 전달하고, 결과는 객체로 받는다. 서비스 내부의 DAO 호출은 기존 계약을 따른다.
- 서비스 인자가 하나면 해당 타입으로 직접 전달한다. 단일 값을 감싸기 위한 DTO나 오버로드는 추가하지 않는다. 무관한 서비스 API까지 일괄 변경하지 않는다.
- 서비스는 응답 DTO를 참조하거나 생성하지 않는다. 조회·가입은 엔티티, 목록은 엔티티 목록, 수정·삭제는 실제 처리 건수를 반환한다. 페이징 정보는 별도 서비스 메소드로 제공할 수 있다.
- 컨트롤러에서 단건 조회의 null, 가입 실패, 수정 처리 건수 및 잘못된 페이지 번호를 확인하고 필요한 HTTP 예외를 직접 던진다. 서비스에 HTTP 예외를 넣거나 단순 CRUD 오류를 위한 별도 예외 핸들러를 만들지 않는다.
- 컨트롤러에서 요청 DTO를 엔티티로 변환해 서비스에 전달하고, 서비스 결과도 컨트롤러에서 응답 DTO 빌더로 직접 매핑한다. DTO에는 `from`, `toEntity` 등의 변환 메소드를 만들지 않는다. 목록 항목도 컨트롤러에서 직접 변환한다. setter 체이닝은 실제로 체이닝을 지원하는 경우에만 사용한다.
- 삭제·수정 결과도 성공 여부, 처리 건수 등 실제 서비스 결과를 담은 응답 객체로 반환한다. 결과 확인 없이 성공 응답을 만들지 않는다.

## 완료 확인

- 요청한 기능의 HTTP 메소드와 기존 URL 계약을 확인하고, 요청·응답 필드명과 타입이 서비스 결과 및 엔티티와 일치하는지 확인한다.
- 컨트롤러의 DTO 입출력, 해당 서비스 호출, 의미 있는 메소드명, 응답의 민감 정보 제외 여부를 검토한다.
- 프로젝트의 빌드 도구로 변경에 맞는 컴파일 및 필요한 기존 테스트를 수행한다. 실행하지 못한 검증은 이유와 함께 알린다.
- 변경한 컨트롤러·서비스·DTO와 검증 결과를 간단히 보고한다.
